### [M-01] The weight-decay bypass in `deployPool` allows any address to force pool deployment when the project's ruleset weight has decayed 10x from the initial weight, enabling an attacker to irreversibly transition the project from accumulation to burn mode at an arbitrary time and with a caller-chosen `terminalToken`.

**Severity**: Medium  **Confidence**: Medium  **Class**: AccessControl
**Location**: `JBUniswapV4LPSplitHook.sol:deployPool:673`

**Exploit Path**

1. Attacker monitors a project that has been accumulating project tokens. 2. Waits (or observes) until the live `currentRulesetOf(projectId).weight * 10 <= initialWeightOf[projectId]`, meaning the ruleset weight has decayed 10x through Juicebox's time-based weight schedule. 3. Calls `deployPool(projectId, terminalToken, 0)` with any valid `terminalToken` that has a non-zero `primaryTerminalOf` for the project. 4. The access-control branch is skipped (condition at line 673 is false), `deployedPoolCount[projectId]++` is set, and the pool is created and seeded. 5. The project is permanently locked in burn mode — all future `processSplitWith` calls burn tokens instead of accumulating. The project owner cannot undo the deployment.

**Setup Transactions**

- Observe target project entering accumulation stage (initialWeightOf set on first processSplitWith call)
- Wait until current ruleset weight has decayed to 1/10th of initialWeightOf[projectId] through natural Juicebox ruleset scheduling

**Exploit Transactions**

- Call deployPool(projectId, terminalToken, 0) — no permission check triggers; pool is deployed at potentially suboptimal time with 0 minCashOutReturn (auto-3% slippage applies)

**Expected Delta**: Project is irreversibly transitioned to burn mode; accumulated project tokens partially cashed out with only 3% slippage protection; LP range set based on JB state at attacker-chosen moment rather than owner-chosen timing

**Reasoning**

1. Line 673: `if (initialWeight == 0 || ruleset.weight * 10 > initialWeight)` — when weight has decayed 10x the branch is skipped, bypassing _requirePermissionFrom
2. initialWeightOf[projectId] is set once in processSplitWith and never updated, so it freezes the initial weight at time of first accumulation
3. Juicebox rulesets have time-based weight decay schedules, so the 10x threshold is reachable after enough ruleset cycles elapse
4. The attacker can choose any valid terminalToken (constrained only by primaryTerminalOf returning non-zero), potentially not the project owner's intended pairing
5. deployedPoolCount is incremented before external calls (reentrancy guard correct), so the state flip is atomic and irreversible
6. Even with minCashOutReturn=0, the auto-slippage at lines 851-857 caps cash-out loss at ~3%, so direct fund loss is bounded but deployment timing and token choice are unilaterally forced by the attacker
7. The project owner loses the ability to choose when and with which terminal token to deploy the pool — a significant protocol governance invariant break

### [M-02] The pre-increment of `_totalOutstandingFeeTokenClaims` in `_routeFeesToProject` uses terminal-token units (e.g. wei of ETH) as a temporary reserve for the fee project token tracker, causing `_burnReceivedTokens` to revert with an arithmetic underflow during any reentrant call in the narrow window between pre-increment and reconciliation when projectToken == feeProjectToken.

**Severity**: Medium  **Confidence**: Low  **Class**: Reentrancy
**Location**: `JBUniswapV4LPSplitHook.sol:_routeFeesToProject:1555`

**Exploit Path**

1. Hook is configured with FEE_PROJECT_ID = P and FEE_PERCENT > 0. 2. Project P (the fee project itself) also has its LP pool managed by this hook, so projectToken[P] == feeProjectToken. 3. collectAndRouteLPFees(P, terminalToken) is called. 4. _burnReceivedTokens(P, feeProjectToken) burns all available feeProjectTokens; after burn: balanceOf(feeProjectToken) == _totalOutstandingFeeTokenClaims[feeProjectToken] = R. 5. _routeFeesToProject is entered: _totalOutstandingFeeTokenClaims[feeProjectToken] += feeAmount (in terminal-token wei, e.g. 1e18). Now _totalOutstandingFeeTokenClaims = R + 1e18 > balanceOf (which is still R JBX). 6. The fee terminal's pay() hook re-enters the hook contract calling collectAndRouteLPFees(P, terminalToken) again. 7. DECREASE_LIQUIDITY(0) is called (no new fees assumed). _burnReceivedTokens(P, feeProjectToken) attempts: balanceOf(R) - _totalOutstandingFeeTokenClaims(R + 1e18) → arithmetic underflow → revert. 8. The outer collectAndRouteLPFees call also reverts, blocking fee collection for the fee project's own pool.

**Setup Transactions**

- Configure hook with FEE_PROJECT_ID = P and FEE_PERCENT > 0
- Create LP pool for project P (fee project itself) through this hook
- Deploy a fee terminal for project P that has a pay hook re-entering collectAndRouteLPFees

**Exploit Transactions**

- Call collectAndRouteLPFees(P, terminalToken) — triggers reentrancy through fee terminal pay hook, causing underflow revert

**Reasoning**

1. Line 1555: _totalOutstandingFeeTokenClaims[feeProjectToken] += feeAmount — feeAmount is in terminal token units (e.g. ETH wei), not fee project token units (e.g. JBX)
2. After _burnReceivedTokens at line 651: balanceOf(feeProjectToken) == _totalOutstandingFeeTokenClaims[feeProjectToken] = R (exactly the reserved amount remains)
3. After pre-increment: _totalOutstandingFeeTokenClaims = R + feeAmount_ETH > R = balanceOf(feeProjectToken)
4. Reentrant _burnReceivedTokens at line 986: balanceOf(R) - _totalOutstandingFeeTokenClaims(R + feeAmount_ETH) underflows in Solidity 0.8 → revert
5. The design intent (comment at line 647-649) states re-entrant _burnReceivedTokens should 'find zero burnable balance', but instead finds an underflow and reverts
6. Requires: (a) fee project's own LP through this hook, (b) fee terminal with malicious/buggy pay hook, (c) projectToken[FEE_PROJECT_ID] == feeProjectToken — very specific conditions

### [M-03] Permissionless collectAndRouteLPFees routes fees to the fee project terminal with minReturnedTokens: 0, allowing any MEV searcher to sandwich the terminal.pay() call and reduce the fee token yield the project receives.

**Severity**: Medium  **Confidence**: Medium  **Class**: MEVEconomic
**Location**: `JBUniswapV4LPSplitHook.sol:_routeFeesToProject:1576`

**Exploit Path**

1. Fee project uses a buyback hook (or any AMM-backed terminal) where pay() minting rate depends on an AMM price. 2. MEV searcher observes a pending collectAndRouteLPFees transaction in the mempool with a significant fee amount. 3. Searcher front-runs with a large swap on the fee project's AMM pool to move the price unfavorably (fewer fee tokens minted per terminal token). 4. collectAndRouteLPFees executes; terminal.pay() with minReturnedTokens: 0 succeeds at the degraded rate; claimableFeeTokens[projectId] is credited with fewer tokens than the market rate would yield. 5. Searcher back-runs to restore their position and pocket the arbitrage profit.

**Setup Transactions**

- Fee project (FEE_PROJECT_ID) is configured with a buyback hook or AMM-backed terminal that determines minting rate from pool price
- LP fees accumulate in the hook's Uniswap v4 position over time

**Exploit Transactions**

- Searcher front-runs: large swap on fee project's AMM to degrade pay() minting rate
- collectAndRouteLPFees executes: terminal.pay(minReturnedTokens=0) succeeds at degraded rate
- Searcher back-runs: restores AMM price and captures arbitrage

**Reasoning**

1. collectAndRouteLPFees is fully permissionless (line 619); any EOA can trigger it at any time
2. _routeFeesToProject passes minReturnedTokens: 0 to terminal.pay() (line 1576/1583); this is documented as an intentional design choice but creates an unconditional MEV surface
3. The fee terminal's pay() minting rate can be an AMM-dependent function if the fee project has a buyback/price hook
4. An adversary can observe the pending collectAndRouteLPFees, sandwich terminal.pay() to manipulate the minting price, and profit from the arbitrage while claimableFeeTokens[projectId] receives fewer tokens
5. The impact is real but bounded: fee tokens (not LP principal) are under-credited; the terminal tokens are consumed regardless
6. Gas profitability threshold limits this to cases where accumulated fees are large enough to justify the sandwich gas cost

### [L-02] When the fee project has no registered terminal for the collected terminal token, `_routeFeesToProject` silently skips the fee amount and leaves it in the contract with no direct on-chain recovery path, effectively permanently stranding those funds.

**Severity**: Low  **Confidence**: High  **Class**: DeltaAccounting
**Location**: `JBUniswapV4LPSplitHook.sol:_routeFeesToProject:1540-1544`

**Exploit Path**

1. Deploy hook with FEE_PROJECT_ID set but no terminal registered for ETH (or whichever terminalToken the pool uses). 2. Anyone calls collectAndRouteLPFees(projectId, terminalToken). 3. TAKE_PAIR deposits LP fees into contract; balances are snapshotted correctly. 4. _routeFeesToProject: feeAmount = amount * FEE_PERCENT / BPS; feeTerminal = primaryTerminalOf(FEE_PROJECT_ID, terminalToken) == address(0). 5. The `if (feeTerminal != address(0))` branch is skipped entirely. 6. remainingAmount = amount - feeAmount is correctly routed to the project. 7. feeAmount worth of terminal tokens remain in the contract with no mapping entry tracking them. 8. Future calls to collectAndRouteLPFees use balance diffs (bal0Before/bal1Before capture the existing balance), so the stranded amount is invisible to future fee collection cycles. 9. Stranded tokens can only be recovered indirectly via rebalanceLiquidity calling _handleLeftoverTokens, which requires SET_BUYBACK_POOL permission and may not be called if no rebalance is needed.

**Setup Transactions**

- Deploy hook clone with FEE_PERCENT > 0 and FEE_PROJECT_ID that has no terminal registered for the pool's terminal token

**Exploit Transactions**

- Call collectAndRouteLPFees(projectId, terminalToken) — fee portion silently stranded

**Expected Delta**: feeAmount = (collected_fees * FEE_PERCENT / BPS) terminal tokens are permanently locked in the hook contract per collection cycle where feeTerminal == address(0)

**Reasoning**

1. Line 1540-1541: feeTerminal looked up from JBDirectory for FEE_PROJECT_ID and terminalToken
2. Line 1544: entire pay() block is inside `if (feeTerminal != address(0))`; if false, feeAmount is never routed
3. Line 1616: only remainingAmount = amount - feeAmount is sent to the project; feeAmount stays in contract
4. Lines 626-643 in collectAndRouteLPFees: bal0Before/bal1Before snapshots capture stranded amounts, so future calls diff from the inflated baseline and never include stranded tokens in amount0/amount1
5. The comment at line 1542-1543 claims recovery is possible by setting a terminal later but provides no code path to re-collect already-stranded amounts
6. _handleLeftoverTokens (line 918, 1484) CAN pick up stranded terminal tokens but requires a privileged rebalanceLiquidity call and will route them to the project balance rather than the fee project — incorrect routing

### [L-06] The two fallback branches in _calculateTickBounds (lines 1029-1032 and 1065-1068) set tickLower and tickUpper relative to a reference tick without clamping to the usable tick bounds, allowing extreme input conditions to produce tick values outside [-887272, 887272] that cause TickMath.getSqrtPriceAtTick to revert and permanently DoS pool deployment or rebalancing for affected projects.

**Severity**: Low  **Confidence**: Medium  **Class**: HookConfiguration
**Location**: `JBUniswapV4LPSplitHook.sol:_calculateTickBounds:1029`

**Exploit Path**

1. Deploy or configure a Juicebox project with cashOutRate = 0 (empty treasury) and an extremely high issuance rate (projectTokensPerTerminalToken near type(uint256).max). 2. Call deployPool() for this project. 3. _calculateTickBounds enters the narrow fallback (lines 1029-1032): issuanceTick gets aligned to 887200, tickUpper = 887200 + 200 = 887400. 4. getLiquidityForAmounts calls TickMath.getSqrtPriceAtTick(887400) which reverts because 887400 > MAX_TICK (887272). 5. deployPool reverts permanently for this project; accumulated tokens are stuck.

**Setup Transactions**

- Create Juicebox project with empty treasury (cashOutRate = 0) and extreme issuance weight producing projectTokensPerTerminalToken > 3.4e38 tokens per terminal token

**Exploit Transactions**

- Call deployPool(projectId, terminalToken, 0) — reverts at TickMath.getSqrtPriceAtTick(887400)

**Reasoning**

1. The primary tick calculation path correctly clamps tickLower/tickUpper to minUsable (-887200) and maxUsable (887000) at lines 1058-1059.
2. The narrow fallback branch at lines 1029-1032 (triggered when cashOutRate == 0 but issuanceRate != 0) does NOT clamp: tickLower = issuanceTick - TICK_SPACING and tickUpper = issuanceTick + TICK_SPACING without any bounds check.
3. If issuanceTick after alignment equals 887200 (the highest valid multiple of TICK_SPACING=200 within MAX_TICK), then tickUpper = 887400 which exceeds MAX_TICK = 887272.
4. TickMath.getSqrtPriceAtTick(887400) reverts in v4 core because 887400 > MAX_TICK.
5. This causes _mintPosition (called from _addUniswapLiquidity) to revert, making deployPool permanently fail for affected projects.
6. Similarly, the second fallback at lines 1065-1068 (triggered when primary path collapses to tickLower >= tickUpper) sets tickLower = currentTick - TICK_SPACING without clamping. If currentTick aligns to -887400 (solidityAlign(MIN_TICK=-887272, 200) = -887400), then tickLower = -887600 < MIN_TICK, causing the same revert.
7. Triggering the path A out-of-bounds requires projectTokensPerTerminalToken ≈ 3.4e38 (extremely high issuance relative to terminal token decimals), which is unrealistic for typical projects but possible in adversarial configurations.
8. Triggering path B requires cashOut and issuance ticks to be identical after alignment AND the current JB price to be near extreme bounds — also an unlikely combination.

### [L-08] collectAndRouteLPFees and rebalanceLiquidity lack a reentrancy guard; the permissionless collectAndRouteLPFees can be re-entered through the fee terminal's pay hook during the _routeFeesToProject → terminal.pay() call, creating a window where re-entrant callers observe inconsistent contract state (position fees already collected, burn already executed, but claimableFeeTokens not yet updated).

**Severity**: Low  **Confidence**: Medium  **Class**: Reentrancy
**Location**: `JBUniswapV4LPSplitHook.sol:collectAndRouteLPFees:619`

**Exploit Path**

1. Attacker controls the fee terminal's pay hook (requires compromised or malicious fee terminal registered in JBDirectory). 2. Any caller invokes collectAndRouteLPFees(projectId, terminalToken). 3. Contract collects fees from position via POSITION_MANAGER, burns project tokens, then calls _routeFeesToProject. 4. _routeFeesToProject pre-increments _totalOutstandingFeeTokenClaims[feeToken] += feeAmount, then calls feeTerminal.pay(). 5. pay() triggers a pay hook that re-enters collectAndRouteLPFees for the same project. 6. Re-entrant call: position already has zero pending fees, _burnReceivedTokens finds zero balance (already burned), _routeCollectedFees with amount0=0 and amount1=0 returns early at line 1512 — no double-extraction occurs. 7. Outer pay() returns, reconciliation sets _totalOutstandingFeeTokenClaims correctly. **Setup Transactions**

- Deploy a malicious fee terminal pay hook that re-enters collectAndRouteLPFees when terminal.pay() is called
- Register this terminal in JBDirectory as the fee project's primary terminal (requires fee project controller access)

**Exploit Transactions**

- Call collectAndRouteLPFees(projectId, terminalToken) — re-entry fires during pay() but short-circuits at zero-fee guard

1. collectAndRouteLPFees is permissionless — any EOA can trigger it at any time
2. The function calls POSITION_MANAGER.modifyLiquidities() to collect fees, then _burnReceivedTokens, then _routeCollectedFees
3. _routeCollectedFees → _routeFeesToProject → terminal.pay() is an external call to the Juicebox fee terminal

6. _burnReceivedTokens in re-entrant call: _totalOutstandingFeeTokenClaims is pre-incremented (inflated) so project tokens are not double-burned

9. However, the absence of a mutex means the invariant relies entirely on the fee terminal's behavior being honest and the zero-fee short-circuit being reachable — a non-standard terminal could subvert this

### [L-09] Silent uint160 truncation in three sqrtPriceX96 helper functions produces an invalid pool initialization price when the computed mulDiv result exceeds 2^160, with no bounds check or revert.

**Severity**: Low  **Confidence**: Low  **Class**: TokenEdgeCases
**Location**: `JBUniswapV4LPSplitHook.sol:_getCashOutRateSqrtPriceX96:376`

**Exploit Path**

1. - Create Juicebox project with extremely large token supply relative to terminal surplus such that token1Amount > 2^128 wei in the price formula

**Exploit Transactions**

- Call deployPool() — the pool is initialized at a truncated/wrong sqrtPrice, LP position tick bounds are computed from the corrupted price, permanently misaligning the LP range

**Reasoning**

1. PRB Math mulDiv() returns uint256 and does not overflow for realistic inputs, but the cast to uint160 at lines 376, 436, and 499 has no bounds check

3. token0Amount is always initialized to _WAD = 1e18, so sqrt(token0Amount) ≈ 1e9
